# Project "Heo & Masuri" — Phase 2 Build Blueprint

> **For the AI implementing this:** You're picking up an in-flight project. Two prior blueprints exist: `BLUEPRINT.md` (Phase 1, shipped) and `BLUEPRINT-PHASE-1.5.md` (Phase 1.5, shipped). **Read both before doing anything.** This document assumes everything in those is live and working. It does not re-explain the architecture, the soft gate, the theme tokens, the `letters` table, or any Phase 1/1.5 conventions.
>
> Phase 2 is built entirely on a **`staging` branch** against a **separate staging Supabase project**, behind Vercel password protection. Phương does not see any of this until merge-to-main at the reveal moment. The implementing AI must respect this isolation throughout.
>
> Phase 2 has had two known recurring problems in past phases that this blueprint actively defends against:
> 1. **Schema drift** — the AI invents column names from fuzzy memory in long sessions
> 2. **Decision drift** — the AI re-litigates settled choices or "improves" things that were deliberate
>
> Section §0 below is the protocol that prevents both. Treat it as non-negotiable.

## §0 — Drift Prevention Protocol (read first, follow always)

The protocol exists because long-running implementation sessions cause the AI to compress memory of the schema, route paths, enum values, and prior decisions. When the AI tries to recall later, it reconstructs from fuzzy memory and produces plausible-sounding-but-wrong code. Section §0 makes the schema and other facts re-derivable from the codebase rather than relying on memory.

### §0.1 Migration discipline

**All schema changes are numbered SQL migration files** in `migrations/`. Never edit an existing migration file. Phase 1 + Phase 1.5 migrations are already in `migrations/` from prior work; Phase 2 migrations start at the next sequential number and never modify earlier files.

Each migration file is named `NNN_feature_name.sql` (zero-padded 3 digits). Each file is idempotent at the statement level where reasonable (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, etc.), but the overall sequence is run exactly once per database.

**Migration workflow for every schema change:**

1. Implementing AI writes `migrations/NNN_feature.sql`
2. Implementing AI reports the file path + full contents in the checkpoint report
3. **Dân (the human) runs the migration manually against the staging Supabase project** — this step does not happen automatically
4. Dân runs `pnpm db:dump` (defined in §0.5) to regenerate `db/schema.sql`
5. Dân runs `pnpm db:types` (defined in §0.5) to regenerate `src/types/database.ts`
6. Dân commits both regenerated files
7. Implementing AI only then proceeds to write code that depends on the new schema

The implementing AI MUST NOT write code that references a migration's tables/columns until step 7. If the AI is uncertain whether the migration has been applied, it asks Dân in the checkpoint report rather than guessing.

### §0.2 Schema re-derivation

The current canonical schema lives in `db/schema.sql` (committed, generated by `pg_dump --schema-only`). The AI is required to read this file before writing any database code in a checkpoint where database code will be written. If the file is missing or stale, the AI stops and asks Dân to regenerate it.

When the AI writes any Supabase query, it does the following first:

```
1. Open db/schema.sql
2. Locate the CREATE TABLE block for the target table
3. Read EVERY column name, type, and default
4. Open src/types/database.ts
5. Locate the type definition for the target table
6. Confirm columns match
7. THEN write the query
```

In the checkpoint report, the AI quotes (verbatim, not paraphrased) the relevant CREATE TABLE block from `db/schema.sql` for every table touched in that checkpoint. This is annoying overhead and that is the point — it forces the consult to actually happen.

### §0.3 TypeScript types from the live database

Supabase generates real TypeScript types from the actual database. Run:

```bash
supabase gen types typescript \
  --project-id <STAGING_PROJECT_REF> \
  --schema public \
  > src/types/database.ts
```

`src/types/database.ts` is committed to the repo, regenerated after every migration. Every Supabase client used in app code is typed:

```typescript
import { createClient } from '@supabase/supabase-js';
import type { Database } from '@/types/database';

const supabase = createClient<Database>(url, key);
```

Untyped Supabase clients are forbidden. ESLint enforces this — any `createClient(` without a generic parameter fails lint.

If the AI references a column that doesn't exist, `tsc --noEmit` rejects the build. **This is the primary defense against schema drift and the reason a checkpoint cannot be marked complete if typecheck fails.**

### §0.4 Decision Log

A complete list of every Phase 2 decision already made, in §1 below. Before proposing alternatives to anything, the AI checks the decision log. If the proposal contradicts a logged decision, the AI does not re-litigate — it raises the conflict in the checkpoint report and asks Dân to either confirm the original or revise it.

The decision log is the authoritative answer to "wait, why did we decide it this way again?"

### §0.5 Required scripts

Add these to `package.json` if not already present:

```json
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "lint": "next lint",
    "db:dump": "supabase db dump --schema public --schema-only > db/schema.sql",
    "db:types": "supabase gen types typescript --project-id $SUPABASE_PROJECT_REF --schema public > src/types/database.ts",
    "db:diff": "supabase db diff",
    "ci:gate": "pnpm typecheck && pnpm lint"
  }
}
```

`pnpm ci:gate` must pass before any checkpoint is marked complete. The AI runs it and reports the exit code.

### §0.6 Canonical references (consult before guessing)

Section §17 of this blueprint contains the complete canonical list of: all new API routes with full path + method + request schema + response schema; all enum-like magic strings; all new env variable names; all Supabase storage bucket names; all Discord webhook env var names; all helper function signatures referenced in this blueprint.

When the AI writes code that uses any of these, it consults §17 first. If something the AI needs is not in §17, it adds it to §17 in the same commit it adds the code, so the next session has it.

### §0.7 The non-obvious choices are marked

Throughout this blueprint, design choices that look "fixable" but are deliberate are marked with `RATIONALE:` blocks. The AI does not "improve" anything marked `RATIONALE:` without explicit permission from Dân, even if it looks suboptimal.

### §0.8 Branch and environment discipline

**All Phase 2 work happens on branch `staging`.** Never on `main`. Never on a feature branch. The `staging` branch is the working branch for the entirety of Phase 2.

`main` is touched ONLY for hotfixes to Phase 1/1.5 production bugs. After any hotfix merges to `main`, the AI (or Dân) merges `main` back into `staging` to keep staging current.

**Two Supabase projects:** the existing production one (used by `main`) and a new staging one (used by `staging`). Two sets of env vars in Vercel. Two sets of Discord webhooks. Two VAPID key pairs (so Phương's existing PWA installation doesn't accidentally subscribe to staging pushes).

Phương MUST NOT see staging. Vercel password protection is enabled on the staging project. The implementing AI never sends a staging URL or staging Discord ping that could route to Phương's phone.

### §0.9 Checkpoint completion criteria

A checkpoint is complete only when ALL of the following are true:

1. `pnpm ci:gate` exits 0
2. The checkpoint report quotes the relevant `CREATE TABLE` blocks from `db/schema.sql` for every table touched
3. The checkpoint report lists every new file created, every file modified, and every migration applied
4. The checkpoint report includes a screen recording (or screenshots if recording infeasible) of the new functionality
5. Dân has reviewed the report and explicitly approved with the word "approved" or equivalent
6. Any `RATIONALE:` blocks relevant to the checkpoint have been respected

If any of the above fails, the checkpoint is rejected and the AI restarts the failing portion.

### §0.10 What to do when stuck

If the AI is uncertain about anything that affects more than a single line of code — schema choice, API shape, animation timing, copy wording, anything — it STOPS and asks Dân. Guessing is the failure mode this entire protocol exists to prevent. There is no penalty for asking, and a significant penalty for guessing.

## §2 — Phase 2 scope (what we're building)

## §4 — Data model additions (Phase 2 migrations)

Naming: continue the existing migration numbering from the Phase 1.5 sequence. The implementing AI checks `migrations/` for the highest existing number and uses the next integer.

Phase 2 introduces ~6 new tables. They are grouped by sub-phase below.

### §4.1 Phase 2A migrations

#### `migrations/NNN_surprise_pool.sql`

Pool of pre-written surprise messages. Used by the surprise drops feature.

```sql
create table surprise_pool (
  id              uuid primary key default gen_random_uuid(),
  body            text not null,
  language        text not null default 'vi' check (language in ('vi','en','mixed')),
  weight          int not null default 1,        -- multiplier for shuffle-bag (higher = picked more often)
  attachments     jsonb,                          -- optional image URL, link, etc.
  author          uuid not null references users(id),  -- always Dân/Masuri for v1
  created_at      timestamptz default now(),
  retired_at      timestamptz                     -- if set, never delivered again
);
create index on surprise_pool (retired_at, created_at desc);

create table surprise_deliveries (
  id              uuid primary key default gen_random_uuid(),
  pool_id         uuid not null references surprise_pool(id),
  letter_id       uuid not null references letters(id),
  delivered_at    timestamptz not null default now(),
  shuffle_round   int not null                    -- which round of the shuffle bag delivered this
);
create index on surprise_deliveries (pool_id, delivered_at desc);
create index on surprise_deliveries (shuffle_round, delivered_at desc);
```

RATIONALE: `surprise_deliveries` exists separately from `letters` because we need to track shuffle-bag state — which items have been used in the current round — without mixing that concern into the generic `letters` table. The `letters` row is the user-visible delivery; the `surprise_deliveries` row is the bookkeeping.

```sql
-- RLS
alter table surprise_pool enable row level security;
alter table surprise_deliveries enable row level security;
-- service-role only for both; no anon policies
```

#### `migrations/NNN_recurring_letters.sql`

Configures GM/GN auto-notes. One row per active recurring schedule.

```sql
create table recurring_letters (
  id                uuid primary key default gen_random_uuid(),
  from_user         uuid not null references users(id),
  to_user           uuid not null references users(id),
  kind              text not null check (kind in ('gm','gn')),
  pool              jsonb not null,                -- array of body strings to rotate through
  send_at_local     time not null,                 -- 07:00 for GM, 22:00 for GN typically
  timezone          text not null default 'Asia/Ho_Chi_Minh',
  enabled           boolean not null default true,
  last_delivered_at timestamptz,
  last_pool_index   int not null default -1,       -- rotates through pool in order; reshuffles at end
  created_at        timestamptz default now()
);
create unique index on recurring_letters (from_user, to_user, kind);
```

RATIONALE: GM/GN content rotates rather than shuffles because the same "Good morning Heo 💕" the same morning is fine; the variation is "Good morning Heo 💕" today vs. "Chào buổi sáng Heo 🌸" tomorrow. Rotation is more predictable than shuffle-bag for daily content.

### §4.2 Phase 2B migrations

#### `migrations/NNN_calendar.sql`

The self-hosted calendar. Three tables: events, the per-user view of "busy", and Masuri's recurring template.

```sql
create table calendar_events (
  id                uuid primary key default gen_random_uuid(),
  owner             uuid not null references users(id),
  start_at          timestamptz not null,
  end_at            timestamptz not null,
  title             text,                          -- nullable: many events are "just busy"
  note              text,
  emoji             text,
  source            text not null default 'manual' check (source in ('manual','recurring_template','date','quick_block')),
  source_ref        uuid,                          -- foreign-keyed by application code based on source
  share_details     boolean not null default false, -- if true, other party sees title/note/emoji
  created_at        timestamptz default now(),
  updated_at        timestamptz default now()
);
create index on calendar_events (owner, start_at);
create index on calendar_events (owner, start_at, end_at);

-- Enforce end > start at DB level
alter table calendar_events add constraint chk_end_after_start check (end_at > start_at);
```

RATIONALE: `share_details` defaults to false. The other party sees only "busy" unless this is flipped on per-event. See decision #7.

```sql
create table recurring_schedule_template (
  user_id           uuid primary key references users(id),
  -- 7-element array, one per day of week (Mon=0, Sun=6)
  -- Each element: array of {start_minute, end_minute} ranges (minutes from midnight, 0-1440)
  template          jsonb not null default '[[],[],[],[],[],[],[]]'::jsonb,
  enabled           boolean not null default false,
  updated_at        timestamptz default now()
);
```

RATIONALE: Stored as minute-from-midnight ranges (e.g., 540-1080 = 9am-6pm) rather than timestamps because the template is recurring and time-of-day-agnostic to date. When applied to a week, app code reads the template and creates `calendar_events` rows for that week with `source='recurring_template'`. Re-applying for a future week is idempotent because the events have unique start_at + owner.

```sql
-- RLS: both users can read each other's events (busy-state visible) but filter share_details server-side
alter table calendar_events enable row level security;
create policy "anon read events" on calendar_events for select to anon using (true);
-- writes are service-role only

alter table recurring_schedule_template enable row level security;
-- service-role only

-- When returning events, the API ALWAYS strips title/note/emoji from events owned by another user
-- where share_details=false. See §6.2.
```

#### `migrations/NNN_important_dates.sql`

Important dates — replaces and generalizes the existing `reunion_dates` table.

```sql
-- Migrate existing reunion_dates rows into important_dates
create table important_dates (
  id              uuid primary key default gen_random_uuid(),
  label_vi        text not null,
  label_en        text not null,
  target_date     date not null,
  kind            text not null check (kind in (
    'reunion',         -- physical meetup planned
    'anniversary',     -- yearly recurrence
    'monthiversary',   -- monthly recurrence on a specific day-of-month
    'birthday_heo',
    'birthday_masuri',
    'other'
  )),
  recurrence      text not null default 'none' check (recurrence in ('none','yearly','monthly')),
  is_current      boolean not null default true,   -- for reunion: only one current; for others: always true
  emoji           text,
  show_on_home    boolean not null default true,
  created_at      timestamptz default now()
);
create index on important_dates (kind, target_date);
create index on important_dates (target_date) where show_on_home = true;

-- Migrate existing reunion_dates rows
insert into important_dates (label_vi, label_en, target_date, kind, recurrence, is_current, show_on_home, created_at)
select
  coalesce(label_vi, 'Ngày đoàn tụ'),
  coalesce(label_en, 'Reunion day'),
  target_date,
  'reunion',
  'none',
  is_current,
  true,
  created_at
from reunion_dates;

-- The reunion_dates table is NOT dropped yet (in case rollback needed)
-- It is dropped in a follow-up migration after Phase 2 ships to production.
```

RATIONALE: Yearly recurrence is computed on the fly (target_date's month+day matches today's month+day), not stored as multiple rows. Monthly recurrence is similar (target_date's day-of-month matches today's day-of-month). This keeps the table small and the recurrence configurable.

```sql
alter table important_dates enable row level security;
create policy "anon read important dates" on important_dates for select to anon using (true);
-- writes service-role only
```

### §4.3 Phase 2C migrations

#### `migrations/NNN_date_idea_bank.sql`

```sql
create table date_ideas (
  id              uuid primary key default gen_random_uuid(),
  added_by        uuid not null references users(id),
  url             text,                            -- the TikTok/Instagram/article URL (nullable for text-only)
  title           text,                            -- auto-fetched from URL or hand-entered
  description     text,
  notes           text,                            -- "looks cute," "for rainy days," etc.
  tags            text[] not null default '{}',    -- ['outdoor','cheap','romantic']
  slot_type       text check (slot_type in ('eat','drink','activity','walk','movie','drive','home','other')),
                                                   -- nullable; many ideas are activity-typed
  thumbnail_url   text,                            -- cached preview image
  archived        boolean not null default false,
  used_count      int not null default 0,          -- how many times this idea was picked
  last_used_at    timestamptz,
  created_at      timestamptz default now()
);
create index on date_ideas (archived, slot_type, created_at desc);
```

## §5 — Phase 2A: Scheduled message infrastructure

### §5.1 The delivery worker

A Vercel Cron job that fires every 5 minutes and delivers due messages.

**Path:** `/api/cron/deliver-scheduled`

**Auth:** Vercel Cron headers (`Authorization: Bearer ${CRON_SECRET}`). Reject all other callers.

**Logic:**

```typescript
// Pseudocode
async function deliverScheduled() {
  // 1. Find letters where scheduled_for <= now() AND delivered_at IS NULL
  const due = await supabase.from('letters')
    .select('*')
    .lte('scheduled_for', now())
    .is('delivered_at', null);

  for (const letter of due) {
    // Respect quiet hours of recipient
    const inQuietHours = await checkQuietHours(letter.to_user);
    if (inQuietHours) continue;  // try again next tick

    // Mark delivered
    await supabase.from('letters')
      .update({ delivered_at: now() })
      .eq('id', letter.id);

    // Fire push
    await pushTo(letter.to_user, {
      title: pushTitleForKind(letter.kind),
      body: previewBody(letter.body, 60),
      url: `/heo/notebook/letter/${letter.id}`,  // or appropriate path by kind
    });

    // Realtime broadcast
    await supabase.channel(`user:${letter.to_user}`).send({
      type: 'broadcast', event: 'letter_delivered', payload: { letter_id: letter.id }
    });
  }
}
```

RATIONALE: A letter that arrives during quiet hours is held until quiet hours end and delivered then. Not delivered late on purpose, not skipped. The `delivered_at` field reflects actual delivery time, not scheduled time, so the recipient sees the delivery happen at a reasonable hour.

`vercel.json`:

```json

  "crons": [
    { "path": "/api/cron/deliver-scheduled", "schedule": "*/5 * * * *" }
  ]
}
```

### §5.3 GM/GN auto-notes

```typescript
async function gmgnTick() {
  const now = currentTimeInTz('Asia/Ho_Chi_Minh');
  const todayKey = now.toISODate();
  const localTime = now.toFormat('HH:mm');

  const matches = await supabase.from('recurring_letters')
    .select('*')
    .eq('enabled', true)
    .eq('send_at_local', `${localTime}:00`);

  for (const rec of matches) {
    // Idempotency: if already delivered today, skip
    if (rec.last_delivered_at &&
        sameDayInTz(rec.last_delivered_at, now, rec.timezone)) continue;

    // Rotate pool
    const pool = rec.pool as string[];
    const idx = (rec.last_pool_index + 1) % pool.length;
    const body = pool[idx];

    // Create letter
    const letter = await createLetter({
      from_user: rec.from_user, to_user: rec.to_user,
      kind: rec.kind,
      body,
      language: 'vi',
      scheduled_for: now,
      delivered_at: now,
    });

    // Update recurring_letters
    await supabase.from('recurring_letters')
      .update({ last_delivered_at: now, last_pool_index: idx })
      .eq('id', rec.id);

    await pushIfNotQuiet(rec.to_user, letterToPush(letter));
  }
}
```

### §6.2 Visibility filter — CRITICAL

`GET /api/calendar/events` returns events for the requested range, but transforms events owned by the OTHER user as follows:

```typescript
function transformForViewer(event: CalendarEvent, viewerId: string): VisibleEvent {
  if (event.owner === viewerId || event.share_details) {
    return event;  // full data
  }
  // Strip private fields
  return {
    id: event.id,
    owner: event.owner,
    start_at: event.start_at,
    end_at: event.end_at,
    title: null,
    note: null,
    emoji: null,
    source: event.source,
    share_details: false,
  };
}
```

This filter runs server-side. The client never receives the private data. This is the privacy promise.

RATIONALE: Doing the filter client-side would mean the data is on the wire and inspectable in DevTools. Server-side stripping is the only honest way to keep details private.

### §7.3 Outfit picker

Route: `/wardrobe` (self) and `/wardrobe/[user]` (other's).

**Add to wardrobe:**

Photo upload via PWA file input (camera or library). Server-side processing:
- Upload to Supabase Storage bucket `wardrobe`
- Generate 200x200 thumbnail (via `sharp` if available, or use a simple canvas-based client-side crop before upload)
- Insert wardrobe_items row

**Browse wardrobe:**

Grid of thumbnails. Tap → fullscreen view with label, tags, "wore on" date list (computed from outfit_suggestions where status='accepted'), edit/archive buttons.

**Suggest to other:**

On the other user's wardrobe page, tap a piece → "Suggest for [date]" sheet. Pick a scheduled date (or "next free overlap" if none scheduled). Optional note. Submit.

This inserts an `outfit_suggestions` row and pushes the recipient. Recipient sees it in their notification feed and on their wardrobe page as a pending suggestion. They can accept (status='accepted'), counter (status='counter', counter_item set), or decline (status='declined' — but soft: copy is "Hôm nay thử cái khác nha" not "rejected").

**Dress code attachment:**

When creating a scheduled date, the form has an optional dress code field. The dress code is shown when picking outfits — the picker UI displays "Dress code: [text] [emoji]" prominently at the top.

### §7.4 Decision flipper / outline builder

Route: `/dates/plan/[date_id]` (one per scheduled date).

UI flow:

1. **Pick template**: grid of the 8 templates. Each shows label, description, slot count. Or "blank" to start empty.
2. **Edit outline**: shows the slots as a vertical list. Each slot is a card showing slot type, label. Drag handles to reorder. `+ Thêm bước` button to insert a slot at any position (opens slot-type picker). Trash icon to remove a slot.
3. **Fill candidates per slot**: each slot card expands to show:
   - "Heo's candidates" subsection: list of date_ideas matching the slot type, with checkboxes. Plus a "+ Add custom" textfield.
   - "Masuri's candidates" subsection: same.
   Both users can fill candidates. Realtime broadcasts so each sees the other's adds.
4. **Spin**: when both feel ready, either taps "Spin 🎲".
   - All-at-once mode (default): the system picks one candidate per slot, animates the spin (slot-by-slot scrolling-ticker style, ~500ms each, sequenced), reveals the final itinerary
   - Slot-by-slot mode (toggle): only spins the first slot; user taps "Next" between each
   - Stores result in `scheduled_dates.itinerary` and stamps `flipped_at`
5. **View itinerary**: shows the picks in order. Each pick is clickable → opens the original date idea (URL, photos, notes).

**Spin algorithm:**

```typescript
function pickForSlot(slot: Slot, candidates: Candidate[]): Pick {
  // All candidates have equal weight by default
  // EXCEPT: candidates with last_used_at within 30 days are weighted 0.3x (don't repeat recently)
  // EXCEPT: candidates with used_count > average are weighted 0.7x (let new things have a chance)
  // Weighted random pick
}
```

RATIONALE: The "don't repeat recently" weighting solves "we always go to the same noodle place" without removing places entirely. The "let new things have a chance" weighting solves "we added 10 new ideas but the wheel keeps picking the same old one."

**Edit after spin:**

The itinerary is mutable. Either user can tap a slot's result → "re-spin this slot" or "pick manually" → choose any candidate or a different date idea. Marked with `manually_overridden: true` in the itinerary JSON for transparency.

The flow:

## §11 — Things to watch for (anti-patterns specific to Phase 2)

1. **Schema drift** — addressed by §0. If the AI catches itself about to write a Supabase query from memory, it stops and re-reads `db/schema.sql` first.

2. **"Improving" the template seed data.** Dân hand-curated the 8 outline templates. The AI does not edit them, reorder them, or "make them more elegant" without asking.

3. **Privacy filter bypass.** The visibility filter in §6.2 is server-side ONLY. If the AI is tempted to do it client-side "for simplicity," that's a bug — the data shouldn't reach the client at all.

4. **Calendar performance.** A week query fetches up to 168 hours × 2 owners = 336 cells. The current schema's index covers this fine. The AI does NOT add caching, materialized views, or other optimization unless `pnpm db:diff` performance testing shows a real problem.

5. **Optimistic UI revert bugs.** When marking busy/free, the UI updates immediately but server can reject. The AI implements the revert path and tests it (simulate network failure, see the cell flip back). Without a revert, a failed mark leaves a phantom busy block.

6. **Date scheduler creating events out of sync with the calendar.** A scheduled date creates a corresponding calendar event. Both rows must be consistent (start_at, end_at). Use a transaction. Updating the date must update the event. Deleting must cascade or refuse.

7. **Outfit photo storage costs.** Wardrobe photos can pile up. Add a soft cap (e.g., 100 items per wardrobe; warn before adding more). Thumbnail generation is required — don't just serve full-res photos in the grid.

8. **iOS Shortcut token leakage.** The shortcut token is a secret. If exposed (e.g., in client code, in commits), it allows arbitrary inserts into date_ideas. Never log it. Never include in error messages. Rotate periodically.

9. **Surprise pool exhaustion edge case.** If the pool is empty and surprise tick fires, gracefully skip and don't error. Log to `#logs`. Suggest to Masuri (via a separate weekly cron or admin UI) when the pool is < 5 unused items.

10. **GM/GN timezone drift.** All recurring_letters use `send_at_local` + `timezone`. The cron computes "is it 07:00 in Asia/Ho_Chi_Minh right now?" — not "is it 07:00 UTC?". Test with VN time and DST transitions (VN doesn't observe DST but the libs should be robust).

11. **Desktop styling making things look like a Windows 98 form.** The cuteness must survive at desktop sizes. Tape, stickers, soft shadows, generous whitespace, real cursors, real focus rings. Don't fall into bare-Tailwind "looks like a CRUD form" energy.

12. **Long-press detection fighting scroll.** On mobile calendar, distinguishing long-press from scroll is hard. Use a touch-start timer that cancels on touch-move > 10px. Don't break the calendar by capturing all touches.

13. **Migrations not idempotent breaks staging-then-production workflow.** Every migration uses `CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, etc. Test by running each migration twice against staging — second run must succeed without changes.

14. **Letters table growing into chaos.** The `letters` table now has 7 kinds. Don't add an 8th in Phase 2 without consulting Dân. If a feature wants a new kind, ask whether it should be a new kind or a new table.
